# Apple design, applied across platforms

Use this skill when a UI change needs Apple HIG guidance without incorrectly imposing Apple conventions on Android or games.
Apple HIG recommendations below are cited at the page that contains the guidance.
This skill distinguishes Apple's platform-specific conventions from transferable design principles and labels its own mappings as synthesis.

## Start by identifying the experience

1. Name every target device, OS, app framework or game engine, and primary input mode before designing; Apple says layouts must adapt to screen size, orientation, window size, multitasking, system features, text size, and locale rather than assuming a fixed canvas ([Layout](https://developer.apple.com/design/human-interface-guidelines/layout)).
2. Identify the highest-priority task and content, then choose the native navigation and input model for each target instead of copying one platform's chrome everywhere ([Layout](https://developer.apple.com/design/human-interface-guidelines/layout), [Navigation and search](https://developer.apple.com/design/human-interface-guidelines/navigation-and-search)).
3. Respect platform safe areas and system gestures, and test different sizes, orientations, text settings, appearances, and input methods ([Layout](https://developer.apple.com/design/human-interface-guidelines/layout), [Gestures](https://developer.apple.com/design/human-interface-guidelines/gestures), [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)).
4. **Author synthesis:** keep a source note for decisions by citing Apple guidance inline at the claim, and label a cross-platform translation or recommendation not stated by Apple as such.

## Device-by-device design checklist

| Device | Layout and spacing | Input and navigation | Type and interaction scale |
| --- | --- | --- | --- |
| **iPhone** | Design for compact width, rotation, safe-area variation, and system UI; allow content to scroll and controls to remain reachable without covering system insets ([Layout](https://developer.apple.com/design/human-interface-guidelines/layout)). | iPhone is typically held in one or both hands, with direct Multi-Touch input and both brief and long sessions; use an iOS tab bar for top-level destinations, not actions, and retain an obvious Back path for hierarchical navigation ([Designing for iOS](https://developer.apple.com/design/human-interface-guidelines/ios), [Gestures](https://developer.apple.com/design/human-interface-guidelines/gestures), [Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars)). | Apple HIG reference body type is 17 pt; use 44 x 44 pt as the normal control target and do not treat the lower 28 x 28 pt platform minimum as the comfortable target ([Typography](https://developer.apple.com/design/human-interface-guidelines/typography), [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility), [Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)). |
| **iPad** | Support rotation, resizable windows, multitasking, and changing width; use a tab bar that can adapt to a sidebar or a split-view sidebar when hierarchy needs it ([Layout](https://developer.apple.com/design/human-interface-guidelines/layout), [Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars), [Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)). | Support touch plus pointer and hardware keyboard; pointer supplements rather than replaces touch, and keyboard focus must make important controls reachable ([Pointing devices](https://developer.apple.com/design/human-interface-guidelines/pointing-devices), [Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards)). | Apple HIG reference body type is 17 pt and normal control target 44 x 44 pt; reflow content rather than clip it when windows or Dynamic Type sizes change ([Typography](https://developer.apple.com/design/human-interface-guidelines/typography), [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility), [Layout](https://developer.apple.com/design/human-interface-guidelines/layout)). |
| **Mac** | Treat the UI as windowed and resizable; do not put critical controls or information at a window's bottom edge, which may be off-screen, or under a camera housing ([Layout](https://developer.apple.com/design/human-interface-guidelines/layout)). | Keyboard and pointer are primary on a large, usually stationary multi-window workspace; use platform menus, toolbars, keyboard navigation, and shortcuts, and ensure hover is never the only way to reveal or activate an important action ([Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/macos), [Pointing devices](https://developer.apple.com/design/human-interface-guidelines/pointing-devices), [Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards), [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). | Apple HIG reference body type is 13 pt; the normal control target is 28 x 28 pt and macOS does not support Dynamic Type ([Typography](https://developer.apple.com/design/human-interface-guidelines/typography), [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). **Author synthesis:** when users need to adjust content size in a Mac app, offer an app-appropriate text-size control. |
| **Apple Watch** | Keep the small wrist display focused on glanceable, concise tasks; people often interact for less than a minute, and HIG guidance is at most three glyph buttons or two short text buttons in one row ([Designing for watchOS](https://developer.apple.com/design/human-interface-guidelines/watchos), [Layout](https://developer.apple.com/design/human-interface-guidelines/layout), [Design and build apps for watchOS 10](https://developer.apple.com/videos/play/wwdc2023/10138/)). | Support touch and use the Digital Crown for scrolling, paging, or precise adjustment; do not make Crown interaction the only way to complete an action ([Digital Crown](https://developer.apple.com/design/human-interface-guidelines/digital-crown), [Design and build apps for watchOS 10](https://developer.apple.com/videos/play/wwdc2023/10138/)). | Apple HIG reference body type is 16 pt, normal control target is 44 x 44 pt, and its accessibility guidance says larger text should ideally reach 140% on watchOS ([Typography](https://developer.apple.com/design/human-interface-guidelines/typography), [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). |
| **Apple TV** | Design for viewing at a distance, keep primary content inside the safe zone, and leave room for focus enlargement; Apple gives margins of 60 pt top/bottom and 80 pt left/right ([Layout](https://developer.apple.com/design/human-interface-guidelines/layout)). | Remote or controller navigation is indirect and focus-based; make directional focus movement predictable and make the focused state visibly distinct ([Remotes](https://developer.apple.com/design/human-interface-guidelines/remotes), [Game controls](https://developer.apple.com/design/human-interface-guidelines/game-controls)). | Apple HIG reference body type is 29 pt; the normal control target is 66 x 66 pt and platform minimum is 56 x 56 pt, reflecting distance and remote-based selection ([Typography](https://developer.apple.com/design/human-interface-guidelines/typography), [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). |
| **Apple Vision Pro** | Choose a window, bounded volume, or immersive space intentionally; the default shared space coexists with other apps, while full space is immersive; keep important content comfortably in view, support resizing, avoid excess windows, and keep readable text predominantly 2D ([Designing for visionOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-visionos), [Spatial layout](https://developer.apple.com/design/human-interface-guidelines/spatial-layout), [Layout](https://developer.apple.com/design/human-interface-guidelines/layout), [Typography](https://developer.apple.com/design/human-interface-guidelines/typography)). | The standard indirect flow is look to target and pinch to select; preserve system gestures and offer alternatives for people who use head or hand Pointer Control ([Gestures](https://developer.apple.com/design/human-interface-guidelines/gestures), [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). | Apple HIG reference body type is 17 pt and normal control target 60 x 60 pt; for regular buttons, keep centers at least 60 pt apart and leave 16 pt or more between them ([Typography](https://developer.apple.com/design/human-interface-guidelines/typography), [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility), [Spatial layout](https://developer.apple.com/design/human-interface-guidelines/spatial-layout)). |

## Apple-platform game guidance, including mobile

Apple publishes a dedicated Designing for games HIG that applies across Apple devices, and it explicitly says to adapt the game to each platform's input and display rather than assume one control scheme ([Designing for games](https://developer.apple.com/design/human-interface-guidelines/designing-for-games)).

- On iPhone and iPad, support touch; use virtual controls when a game has many actions or movement demands, but prefer direct interaction with game objects when it is clearer and avoids covering play content ([Game controls](https://developer.apple.com/design/human-interface-guidelines/game-controls)).
- Place mobile game buttons within comfortable thumb reach and safe areas, avoid the Home indicator and Dynamic Island, and avoid covering expected movement or camera-control zones; put secondary controls such as menus near the top ([Game controls](https://developer.apple.com/design/human-interface-guidelines/game-controls)).
- Support the platform's common default input and, where appropriate, physical controllers as an additional option; Apple notes not every player can use a controller ([Designing for games](https://developer.apple.com/design/human-interface-guidelines/designing-for-games), [Game controls](https://developer.apple.com/design/human-interface-guidelines/game-controls)).
- Apply each platform's text and control-size guidance to in-game UI as well as menus, and test game text on every supported display ([Designing for games](https://developer.apple.com/design/human-interface-guidelines/designing-for-games), [Typography](https://developer.apple.com/design/human-interface-guidelines/typography)).
- Use good accessibility defaults and let players personalize type size, control mapping, motion intensity, and sound balance; do not rely on color alone or make important narrative information available only in an uncaptioned cutscene ([Designing for games](https://developer.apple.com/design/human-interface-guidelines/designing-for-games)).
- **Author synthesis:** Apple's game guidance defines platform-facing experience, not Godot's implementation API; apply the Apple input/accessibility target to the Apple build and use the game engine's native controls, themes, focus, and input systems for implementation ([Designing for games](https://developer.apple.com/design/human-interface-guidelines/designing-for-games), [Godot UI](https://docs.godotengine.org/en/stable/tutorials/ui/index.html), [Godot UI navigation](https://docs.godotengine.org/en/stable/tutorials/ui/gui_navigation.html)).

## What transfers, and what does not

The mappings in this table are **author synthesis**, not Apple requirements for Android or game engines.
The cited Apple page is the source principle; Android and Godot links name a closer native implementation, not an instruction to imitate Apple's appearance.

| Apple convention | Scope and transfer | Nearest fit elsewhere |
| --- | --- | --- |
| **SF Symbols and SF fonts** | Apple-only asset and typography systems; use them only where licensed and supported on Apple platforms ([SF Symbols](https://developer.apple.com/design/human-interface-guidelines/sf-symbols), [Typography](https://developer.apple.com/design/human-interface-guidelines/typography)). | Android: Material Symbols and Android typography; Godot: project-owned icon set and theme fonts. Keep symbol meaning consistent, not artwork identical ([Material Symbols](https://fonts.google.com/icons), [Godot UI skinning](https://docs.godotengine.org/en/stable/tutorials/ui/gui_skinning.html)). |
| **Apple tab bars and sidebar adaptation** | The behaviors and placement are platform-specific; the transferable idea is stable, visible top-level navigation that fits information structure ([Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars), [Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)). | Android: Material navigation bar on compact layouts and rail/drawer on larger layouts; Godot: engine-native Control/Container composition, not a mandatory app tab pattern ([Android responsive navigation](https://developer.android.com/develop/ui/views/layout/build-responsive-navigation), [Godot UI](https://docs.godotengine.org/en/stable/tutorials/ui/index.html)). |
| **Dynamic Type** | Apple system feature and API, not a cross-platform name or sizing unit; the portable principle is user-controlled text scaling and reflow ([Typography](https://developer.apple.com/design/human-interface-guidelines/typography), [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). | Android: scalable `sp` text and system font scaling; Godot: scalable theme font sizes and layout that responds to the project's accessibility settings ([Android accessibility](https://developer.android.com/design/ui/mobile/guides/foundations/accessibility), [Godot Control](https://docs.godotengine.org/en/stable/classes/class_control.html)). |
| **Liquid Glass** | Apple-specific material and system appearance; do not copy its refraction/translucency as a universal design law, and do not apply it to Apple's content layer ([Materials](https://developer.apple.com/design/human-interface-guidelines/materials)). | Android: use Material surfaces and elevation as Android intends, not a fake Liquid Glass skin; Godot: use its theme and rendering/material controls where they improve hierarchy ([Material Design 3 in Compose](https://developer.android.com/develop/ui/compose/designsystems/material3), [Godot UI skinning](https://docs.godotengine.org/en/stable/tutorials/ui/gui_skinning.html)). |
| **Apple point sizes and safe areas** | The values in the device table are Apple's points and platform recommendations, not dp, sp, CSS px, or a universal cross-platform token set ([Layout](https://developer.apple.com/design/human-interface-guidelines/layout), [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). | Translate the intent using each platform's own density-independent units, window insets, safe areas, display scale, and accessibility settings; Android's 48 dp control target is distinct from Apple's 44 pt recommendation ([Android touch targets](https://developer.android.com/develop/ui/compose/accessibility/api-defaults)). |
| **Apple app icons and icon tooling** | Icon Composer, Apple icon layers, and Apple-specific system treatments apply to Apple distribution targets ([App icons](https://developer.apple.com/design/human-interface-guidelines/app-icons), [Design Resources](https://developer.apple.com/design/resources/)). | Android: make platform-appropriate adaptive icons; a Godot game uses target-store icon assets, with engine/platform packaging guidance rather than the Apple icon format ([Android adaptive icons](https://developer.android.com/develop/ui/views/launch/icon_design_adaptive)). |
| **Apple remote, Crown, and gaze conventions** | These inputs are specific to Apple TV, Apple Watch, or visionOS; transfer the principle of designing for the real primary input, not those exact gestures ([Remotes](https://developer.apple.com/design/human-interface-guidelines/remotes), [Digital Crown](https://developer.apple.com/design/human-interface-guidelines/digital-crown), [Gestures](https://developer.apple.com/design/human-interface-guidelines/gestures)). | Android TV and game controllers need explicit D-pad/controller focus; Godot provides keyboard/controller focus navigation, while XR should use the project's native spatial input model ([Godot UI navigation](https://docs.godotengine.org/en/stable/tutorials/ui/gui_navigation.html)). |

## Numbers, requirements, and design targets

Treat measurements as platform-relative points unless the source names another unit.
Do not convert a point value directly into Android dp, web CSS pixels, or game-engine pixels.

| Measure | Apple's current HIG guidance | How to apply it |
| --- | --- | --- |
| Control target by platform | Recommended defaults: iOS/iPadOS 44 x 44 pt, macOS 28 x 28 pt, tvOS 66 x 66 pt, visionOS 60 x 60 pt, watchOS 44 x 44 pt; listed minimums are respectively 28, 20, 56, 28, and 28 pt ([Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). | Aim for the recommended target; the HIG calls these recommended default/minimum sizes, not a universal App Review pass/fail rule. Buttons say 44 x 44 pt generally and 60 x 60 pt in visionOS ([Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)). |
| Space around controls | About 12 pt around bezel controls and 24 pt around visible edges for controls without a bezel; visionOS regular buttons should have centers at least 60 pt apart and at least 16 pt clear space ([Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility), [Spatial layout](https://developer.apple.com/design/human-interface-guidelines/spatial-layout)). | Use the spacing as an Apple-platform starting point, then test real target sizes, visual separation, and input precision. |
| Body text reference / minimum | iOS/iPadOS 17/11 pt, macOS 13/10 pt, tvOS 29/23 pt, visionOS 17/12 pt, watchOS 16/12 pt ([Typography](https://developer.apple.com/design/human-interface-guidelines/typography)). | Apple says to use recommended defaults and minimums for custom as well as system fonts; prioritize comfort and testing over treating the minimum as a desired design size. |
| Text enlargement | Apple says ideally support enlargement of at least 200%, or 140% for watchOS ([Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). | This is explicitly an ideal, not phrased as a universal hard requirement; test that layouts reflow rather than crop or overlap. |
| Contrast | Apple Accessibility Inspector uses WCAG AA guidance: up to 17 pt requires 4.5:1; 18 pt or any bold text uses 3:1 ([Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). App Store Connect's Sufficient Contrast evaluation generally expects 4.5:1 for most text in common tasks and asks teams to test both light and dark modes ([Sufficient Contrast evaluation criteria](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/sufficient-contrast-evaluation-criteria/)). | Apply the stricter 4.5:1 target to ordinary text unless the documented large/bold exception applies; check real text, controls, icons, translucency, both appearances, and Increase Contrast. |
| TV safe zone | 60 pt top/bottom and 80 pt sides ([Layout](https://developer.apple.com/design/human-interface-guidelines/layout)). | This is specific to the Apple TV guidance, not a margin to reuse on phones, Android TV, or web. |
| Corner radii and spacing systems | Apple discusses concentric shapes and platform system materials, but the cited HIG does not define one universal corner radius or one universal spacing scale for every custom app ([Materials](https://developer.apple.com/design/human-interface-guidelines/materials), [Get to know the new design system](https://developer.apple.com/videos/play/wwdc2025/356/)). | Do not invent or cargo-cult numeric radii; use the actual component library and visual context for each target. **Author synthesis.** |

### Hard requirements versus preferences

Apple HIG frequently frames values with words such as “strive,” “in general,” “consider,” and “ideally”; treat those as design targets unless the relevant platform/API or a separate policy makes them mandatory ([Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility), [Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)).
App Review is a separate policy surface: guideline 2.1 says submissions should be final and functional and that incomplete bundles or binaries with crashes or obvious technical problems will be rejected ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines)).
Guideline 4.2 is the relevant minimum-functionality risk for an app that does not provide sufficient app-like value; do not turn this into the false rule that every web-backed or WebView feature is prohibited ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines)).
Accessibility Nutrition Labels are claims about support for common tasks, so do not claim support that the real experience does not provide ([Accessibility Nutrition Labels](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/overview-of-accessibility-nutrition-labels/)).

## Practical review checklist

- **Layout:** exercise each supported size, orientation, window resize, split/multitasking configuration, safe area, locale/RTL, and larger text; check no important content is clipped, hidden, or horizontally scrolling unnecessarily ([Layout](https://developer.apple.com/design/human-interface-guidelines/layout)).
- **Navigation and inputs:** test every destination and return path using all intended inputs; keep standard gestures predictable and provide another path for important actions that would otherwise depend on a custom gesture, hover, pointer precision, gaze, or controller focus ([Gestures](https://developer.apple.com/design/human-interface-guidelines/gestures), [Pointing devices](https://developer.apple.com/design/human-interface-guidelines/pointing-devices), [Remotes](https://developer.apple.com/design/human-interface-guidelines/remotes)).
- **Accessibility:** test VoiceOver names/order/actions, text enlargement, Increase Contrast, light/dark appearance, non-color status cues, captions or text equivalents for important audio/video information, and reduced-motion needs ([Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility), [Motion](https://developer.apple.com/design/human-interface-guidelines/motion), [Color](https://developer.apple.com/design/human-interface-guidelines/color)).
- **Visual system:** prefer native components where they fit; use color consistently, avoid Liquid Glass in content, use motion only when purposeful and optional, and check icon meaning and typography at actual rendered sizes ([Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons), [Color](https://developer.apple.com/design/human-interface-guidelines/color), [Materials](https://developer.apple.com/design/human-interface-guidelines/materials), [Motion](https://developer.apple.com/design/human-interface-guidelines/motion), [SF Symbols](https://developer.apple.com/design/human-interface-guidelines/sf-symbols)).
- **Game UI:** verify text and controls at real play distance and under the supported input; do not assume the interface is a native phone app merely because the game runs on a phone ([Typography](https://developer.apple.com/design/human-interface-guidelines/typography), [Motion](https://developer.apple.com/design/human-interface-guidelines/motion), [Game controls](https://developer.apple.com/design/human-interface-guidelines/game-controls)).
- **Review risk:** before an Apple submission, remove placeholders, ensure essential functionality and review credentials work, and test the released binary on devices; Apple explicitly calls out incomplete content and crashes under guideline 2.1 ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines)).

## Guidance that changes or appears to conflict

- The older general UI Design Dos and Don’ts page says tap targets should be at least 44 pt, while the newer Accessibility table gives a recommended default and separate minimum for each platform and Buttons calls out 60 x 60 pt in visionOS ([UI Design Dos and Don’ts](https://developer.apple.com/design/tips), [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility), [Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)). Resolve this by using the platform-specific HIG values, retaining 44 pt as the familiar iOS target, and never describing the lower minima as the preferred target.
- Older platform guidance and screenshots can predate current navigation and material behavior; Apple's “What's new” page records changes, while current Tab bars, Sidebars, and Materials pages define today's guidance ([What's new](https://developer.apple.com/design/whats-new), [Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars), [Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars), [Materials](https://developer.apple.com/design/human-interface-guidelines/materials)).
- A native component can inherit new system styling while custom styling can diverge; Apple recommends using standard framework components for automatic platform updates and keeping Liquid Glass reserved for the functional UI layer ([Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass), [Materials](https://developer.apple.com/design/human-interface-guidelines/materials)).
- Apple's Designing for games overview describes visionOS gameplay input as eyes and hands with direct and indirect gestures, while its default-input table labels visionOS input as “Touch”; treat the table label as less specific, consult the dedicated [visionOS Gestures guidance](https://developer.apple.com/design/human-interface-guidelines/gestures#visionOS), and verify the actual target interaction instead of assuming physical touchscreen input ([Designing for games](https://developer.apple.com/design/human-interface-guidelines/designing-for-games)).
- HIG guidance, contrast-evaluation criteria, and App Review rules are not interchangeable: cite the exact source and label a recommendation, evaluation criterion, or explicit rejection condition correctly ([Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility), [Sufficient Contrast evaluation criteria](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/sufficient-contrast-evaluation-criteria/), [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines)).

## Source shelf

Use the current HIG page as the primary Apple reference and follow its linked platform and component pages when the UI change needs more detail.
Apple maintains design downloads, fonts, platform UI kits, icons, and SF Symbols in [Apple Design Resources](https://developer.apple.com/design/resources/).
Apple's dedicated cross-platform game guidance is [Designing for games](https://developer.apple.com/design/human-interface-guidelines/designing-for-games).
The HIG landing page and revision log are at [Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines) and [What's new](https://developer.apple.com/design/whats-new).
